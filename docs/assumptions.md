# Assumptions

This file lists the removable parts of CAVU: code that makes up for a weakness of today's models and sits behind a switch, so it can be deleted when models no longer need it. Every removable part has an entry here, landed with its code, naming its switch, what the switch turns on, the assumption the part rests on, and the replay comparison that would retire it. `cavu replay --name NAME` runs the comparisons: it re-runs the tasks marked with `cavu task mark` under a configuration and prints each against the previous replay.

It also lists what the Claude Code adapter assumes of the pinned Claude Code version. Those entries have no switch: they change when the pinned version changes, and name the check against a new release that would change or retire them, run by the conformance suite (`make test-integration`).

## continuations

- Switch: `continuations`, set per project and overridden by a task's overrides, which is how the `internal/replay` package sets it. On by default.
- What it turns on: when an agent session ends unfinished or crashed, the engine resumes the same session in continue mode, at most 2 times since the last human action on the task. With the switch off, such a session stops the task as `agent_error`.
- Assumption: current models sometimes end a turn with a progress report instead of finished work.
- Comparison to retire it: replay the same reference set with the switch off. Retire the part when the verify pass rate and the turns used are no worse than with it on.

## verify_fix

- Switch: `verify_fix`, set per project and overridden by a task's overrides, which is how the `internal/replay` package sets it. On by default.
- What it turns on: when the verify command fails or times out, the engine resumes the same session in fix mode with the recorded verify output (at most 64 KiB, its head and tail kept), at most 2 rounds since the last human action on the task. With the switch off, the task stops as `verify_failed`.
- Assumption: a second attempt after a failed verify usually succeeds.
- Comparison to retire it: replay the same reference set with the switch off. Retire the part when the verify pass rate and the turns used are no worse than with it on.

## web_tools

- Switch: `web_tools`, set per project and overridden by a task's overrides, which is how the `internal/replay` package sets it. Off by default.
- What it turns on: the agent's web tools. With the switch off, the Claude Code adapter disallows `WebFetch` and `WebSearch` and sets `CLAUDE_CODE_DISABLE_WEB_FETCH=1`, so a session can neither fetch a page nor search the web.
- Assumption: fetched content is an injection and exfiltration channel: current models can follow instructions planted in a page they read, and a request they send can carry the repository's content out.
- Comparison to retire it: replay the same reference set with `cavu replay --web-tools`, with tasks whose fetched pages carry planted instructions. Retire the part when no session follows a planted instruction or sends the repository's content out, and the verify pass rate is no worse than with it off.

## readiness

- Switch: `readiness`, set per project and overridden by a task's overrides, which is how the `internal/replay` package sets it (`cavu replay --no-readiness`). On by default.
- What it turns on: a readiness turn opens each run's session. The agent reads the task and what it needs of the repository in the read-only phase, whose workspace is mounted read-only, and ends `ready`, or `blocked` with a question for each fact it needs that neither the task nor the repository holds, a contact or any other commitment made in the owner's name counting as one, and the answer it would assume. `ready` resumes the same session in the agent phase to do the task. `blocked` stops the task as `question`, which a person answers as any other, and the answer resumes the session with every tool. A replay answers a shadow's readiness questions with the agent's own suggested answers when it gave one for every question, and counts the questions. With the switch off, the session opens with the task.
- Assumption: models start unattended work without asking for missing facts.
- Comparison to retire it: replay the same reference set with `cavu replay --no-readiness`. Retire the part when the questions it asked did not change what a person had to correct, and the verify pass rate is no worse than with it on.

## review

- Switch: `review`, set per project and overridden by a task's overrides, which is how the `internal/replay` package sets it (`cavu replay --no-review`). On by default.
- What it turns on: once a change passes verify, or its verify is waived, a fresh reviewer session in the read-only phase, in the review role (`model_review` and `effort_review`, each the work value when unset). It reads the task, a person's answers, the agent's assumptions, the agent's summary as a claim to check, and the diff, is told the change passed the verify command, which it names, or that the project waives verify, and gives two verdicts, whether the change does what the task asked, nothing missing and nothing extra, and whether it is well built, with findings, each `critical`, `important` or `minor`. The gate: a critical or important finding, or a failed first verdict, starts a fix round; minor findings are recorded and never do. A fix round is a fix session, the verify gate, then a scoped review, a fresh session that rules each open finding addressed or not from the fix's diff, reports what the fix broke and raises nothing on code the fix did not touch. At most five rounds since the last human action: rounds 1 to 3 resume the working session with the open findings, rounds 4 and 5 start a fresh session in the strong role (`model_strong` and `effort_strong`, each the work value when unset) with the task, the diff and the open findings. Nothing is dropped when the rounds end, at the cap or when a fix session changes nothing: the change is exported with the findings left open and the minor ones, which `cavu task show` prints. A review that gives no verdict exports the change without one and says why; a usage limit, an endpoint failure, a timeout, used-up turns or a spend the proxy cannot count stop the task as they stop a work session. With the switch off, a change that passes verify is exported.
- The diff the reviewer reads: before the session, CAVU makes a bundle of the task branch in the read-only container and imports it into the project's mirror in a fresh container that mounts none of the run's volumes, where git runs under no configuration the agent wrote. There git writes `/run/cavu/review.patch`, its summary and the diff from the base commit to the frozen head, without binary patches, so a built binary is one line, and CAVU copies it into the read-only container. A scoped review also gets `/run/cavu/fix.patch`, from the head the previous review saw. A bundle the import refuses leaves the review without a verdict. A fresh fix session gets `review.patch` computed in the workspace the agent worked in, in the agent phase, with diff options that keep git from running a program the repository names: the agent's configuration applies there, and can mislead only the agent.
- Assumption: a fresh reviewer finds defects the working session misses, and a second or later fix round still improves the result.
- Comparison to retire it: replay the same reference set with `cavu replay --no-review`, and have a person read both diffs of each task. Retire the part when the reviewed diffs are no better and the findings left open were not ones the person agreed with.

## The pinned flag set of the Claude Code adapter

- Switch: none. The flags and the environment are constants in `internal/driver/claudecode`, changed when the pinned Claude Code version changes.
- What it turns on: every session runs `claude` with
  - always: `-p --output-format stream-json --input-format stream-json --verbose --include-partial-messages --setting-sources user --strict-mcp-config --system-prompt-snapshot off --permission-mode bypassPermissions`, `--model <id>`, `--settings <file>` with a settings file that turns commit and PR attribution and every hook off, `--session-id <uuid>` or `--resume <id>`, and `--max-turns <n>`;
  - when the session sets them: `--effort <level>`, `--append-system-prompt-file <file>` holding its instructions, and `--json-schema <schema>` for a structured result;
  - unless the session allows web tools: `--disallowedTools WebFetch WebSearch`;
  - for a read-only session: `Edit`, `Write` and `NotebookEdit` in `--disallowedTools`, so no turn goes to an edit that must fail. The shell stays, since on the pinned version it is how an agent searches. What keeps the session from changing anything is the sandbox, not the tool list: it runs in the read-only phase, whose workspace is mounted read-only;
  - an environment built whole: `HOME`, `CLAUDE_CONFIG_DIR`, `PATH`, `DISABLE_UPDATES=1`, `DISABLE_AUTOUPDATER=1`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, `CLAUDE_CODE_DISABLE_FAST_MODE=1`, `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, `CLAUDE_CODE_DISABLE_WEB_FETCH=1` unless the session allows web tools, the auth mode's variables (`CLAUDE_CODE_OAUTH_TOKEN`, or `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN`), none of the other auth or provider variables the caller's environment may hold, and the loopback hosts in `NO_PROXY` and `no_proxy` when the caller's environment names a proxy;
  - a cleared config directory and staged instruction files: before every session the driver empties the config directory but for the transcripts (`projects/`), then writes into it the instance's instruction file and skills (the `instructions_path` and `skills_path` settings) and, when the session names a base commit, the repository's root instruction files, rules and skills from that commit. The instance's instructions open the one staged instruction file, before the repository's, and the repository's skills are written after the instance's, so a repository skill of the same name is written over the instance's;
  - a sandbox check: both run only through `/etc/cavu/sandbox`, a file only the sandbox image carries, and a session in an image without it stops with an error naming `cavu image build`. `internal/driver/claudecode/stage.go` holds how the clear, the staging, their limits and the check work.
- Assumption: on the pinned version these flags and variables give user-level settings only and a clean headless run. The pinned version reads a repository's `CLAUDE.md`, `AGENTS.md` and skills only with the project settings source, which also applies the repository's own settings file (its environment, permission rules and hooks), so the staging gives the agent those files through the user source instead.
- Check to change or retire it: run the conformance suite against each new release. Change a flag or variable when the suite fails, and drop one once a release makes it unnecessary. `TestInstructionsNeedStaging` runs a session without staging and wants none of the repository's instruction files in any request; when it fails, the release loads them without the project source, and the staging goes. `TestLiveSubscriptionHosts` logs every host a subscription run asks for beyond the adapter's `Hosts`; on 2.1.325 it logged none. `TestReadOnlySessionChangesNothing` runs a read-only session in the read-only phase and wants none of the three editing tools in its init line or in any request's tool definitions, the workspace unchanged after scripted `Write`, `Edit` and shell `touch` calls, and a shell `grep`'s output in the next request; `TestReadOnlyThenResumeWrites` resumes such a session in the agent phase and wants its scripted `Write` to land.

## The stream the Claude Code adapter reads

- Switch: none. The mapper (`internal/driver/claudecode/mapper.go`, `ratelimit.go`, `run.go`) rests on these facts about the pinned version's `stream-json` output. A release that changes one changes what a person is told, or what is recorded as success.
- Usage limit: a `result` line with `is_error` true is a usage limit and maps to `usage_limit` when its `api_error` is `usage_limit_reached`, whatever its text or status, outside an authentication failure. Without the code, it is one when `api_error_status` is 429 and the text opens with `You've hit your ` or contains `usage limit` (`isUsageLimitText` in `ratelimit.go`, `outcome` in `mapper.go`). The 2.1.325 binary carries `usage_limit_reached` (`grep -a -c` in the image finds it on 4 lines), but its result line was not recorded. The reset time is the `resetsAt` of the last `rate_limit_event` of the run. A session is never stopped on a `rate_limit_event`: a `rejected` event is recorded on 2.1.326 right before the limit result, and an unverified report says accounts with overage enabled get one on requests that still succeed, so the mapper reports the event and goes on to the result. Observed on 2.1.326 (`real/weekly-limit.jsonl`): a weekly limit is a `rejected` `seven_day` event with the reset time, a synthetic assistant line, then an error `result` with `subtype` `success`, status 429, `api_error` `usage_limit_reached` and the limit text. Not observed: the five-hour window, an account with overage, and whether the newer texts end a run. A 429 with neither the code nor the text maps to `endpoint`. The text prefix and the six window names are in the 2.1.325 binary (`grep -a` in the image finds `5-hour limit`, `weekly limit`, `Opus limit`, `Sonnet limit`, `Fable limit` and `usage credit limit`); no mock answer reaches the text, so no conformance test sees a real usage limit. The newer texts `You've reached your` and `You're out of usage credits` are not matched.
  - Check: none reaches an exhausted window on purpose. `TestMapperUsageLimitFixture` maps the recorded result with the code, the text and neither, `TestErrorResults` pins the 429 without the text, and the opt-in `TestLiveRateLimitEventShape` wants a window and a reset time in a real event. A run at an exhausted window settles the rest.
- Success: judged by `is_error`, never `subtype`. An authentication failure reports `subtype: "success"` with `is_error` true. Check: `TestResultFields`, `TestErrorResults`; `real/t2.jsonl` is the recorded case.
- Authentication failure: a result with `api_error_status` 401, a result text that opens with `Not logged in`, or an assistant line with `error: "authentication_failed"` maps to `auth`. Check: `TestErrorResults` for the 401; the text and the assistant line are only in `real/t2.jsonl`.
- Synthetic messages: an assistant line whose model is `<synthetic>` is a message Claude Code made up locally and is not counted as a model call. Check: `real/t2.jsonl`.
- Resumed sessions: `model_usage_since_last_result` is the share of the process that wrote it, where `modelUsage` and `total_cost_usd` are cumulative over the resumed session; the mapper takes the share and falls back to the cumulative fields when it is missing. Check: `TestResumeAcrossContainers` runs a resume; the field itself is read in `two_models.jsonl` and `real/t5.jsonl`.
- Refused resume: `--resume` of a session with no transcript ends with an error result and `No conversation found` on stderr, and maps to `resume_refused`. Check: `TestResumeUnknownSession`.
- Rate limit event: a live `rate_limit_event` carries `status`, `resetsAt`, `rateLimitType`, `overageStatus`, `overageDisabledReason`, `isUsingOverage` and `unifiedWindows` with each window's `utilization`, `resetsAt` and `status`, as recorded on 2.1.322 and 2.1.326. Against a mock it is only `{"status":"allowed","isUsingOverage":false}`. Check: `TestLiveRateLimitEventShape` passed on 2.1.325.
- Subagents: the subagent tool is `Agent`, whose input requires `description` and `prompt`, and a subagent runs in the foreground, its requests between the main session's, on the session's model when the call names none of the `model` input's `sonnet`, `opus`, `haiku` or `fable`. Its model calls are in the result's `modelUsage` and `model_usage_since_last_result`, which the mapper takes `Result.Usage` from, and in the proxy's count; the result's top-level `usage` holds only the main session's calls. Its turns count toward neither `num_turns` nor `--max-turns`: a session whose own two turns fit `--max-turns 2` ends done under it after a subagent's two more, and reports 2 turns. The runner ends the whole `claude` process at the session's time limit, so that limit bounds a subagent and `--max-turns` does not. Probed in key mode; a subscription run is not probed. Check: `TestSubagentIsCounted` asserts the order of the requests, `Result.Usage`, the proxy's count, how the run ends and `num_turns`; the tool's input, the subagent's model and the top-level `usage` were observed on 2.1.325.
- Budget flag: `--max-budget-usd` stops a subscription run with an error result of `subtype` `error_max_budget_usd` and `terminal_reason` `budget_exhausted`, the limit in `errors` and a per-model cost whose `costBasis` is `list`. The mapper has no case for it and maps it to `crashed`; CAVU passes no budget flag. Check: `TestLiveBudgetFlagUnderSubscription` logged it on 2.1.325.

## Unknown on 2.1.325

What a mock cannot settle. Each live check (`live_test.go` in `internal/driver/claudecode`, and `live_integration_test.go` in `internal/runner`, tags `integration` and `live`) skips unless its variables are set, and never runs in CI:

```bash
CAVU_LIVE_SUBSCRIPTION_TOKEN=... go test -tags integration,live -count=1 -run 'TestLive' ./internal/driver/claudecode/
CAVU_LIVE_ENDPOINT_URL=... CAVU_LIVE_ENDPOINT_KEY=... go test -tags integration,live -count=1 -run 'TestLiveGateway' ./internal/driver/claudecode/
CAVU_LIVE_SUBSCRIPTION_TOKEN=... go test -tags integration,live -count=1 -run 'TestLiveReadinessAsks' ./internal/runner/
```

`CAVU_LIVE_ENDPOINT_AUTH_HEADER` (`bearer` or `x-api-key`, default `x-api-key`) and `CAVU_LIVE_MODEL` (default `claude-haiku-5-5`) adjust them.

| Question | What would settle it |
|---|---|
| The usage-limit `result` line on 2.1.325 itself (the weekly one is recorded on 2.1.326 only), the other windows, a `rejected` event on an account with overage, and whether the newer texts end a run | a subscription run at an exhausted window; no live check reaches one on purpose |
| Cache reads through a real gateway | `TestLiveGatewayCacheReads`: the sidecar's meter must count cache reads on the second of two turns |
| A tail of stderr cut inside the token, or a form of it, keeps a fragment no mask can recognise | not reachable: no check saw a token on stderr in any form |
